# Omarchy Hooks State Design

**Status:** Approved design
**Date:** 2026-09-04
**Project:** `omarchy-blueprint`
**Target profile schema:** 5
**Prerequisite:** Merge the schema-4 Shell-state milestone before implementation.

## Summary

Add a first-class `hooks` provider that captures, diffs, restores, verifies, and validates Omarchy automation hooks stored under `~/.config/omarchy/hooks`.

Hooks are executable behavior, not ordinary configuration. Blueprint therefore treats every hook restore as high-risk, preserves exact source bytes and desired Unix permission bits, never overwrites unknown target content, never removes extra target hooks, and never executes a hook during restore or verification.

The provider follows the current Omarchy runtime rather than a hard-coded list of documented events. It supports both runtime forms:

```text
~/.config/omarchy/hooks/<event>
~/.config/omarchy/hooks/<event>.d/<hook>
```

Unknown event names are allowed so Blueprint remains forward-compatible when Omarchy adds new hook events.

## Current Omarchy contract

The design is based on the current Omarchy Quattro hook implementation.

`bin/omarchy-hook`:

- resolves a flat hook at `~/.config/omarchy/hooks/<name>`;
- runs the flat hook first when it is a regular file;
- then scans `~/.config/omarchy/hooks/<name>.d/`;
- runs immediate regular files from that directory in shell-glob order;
- skips `*.sample` entries in the `.d/` form;
- does not recurse into nested directories;
- invokes hook source using `bash "$hook"`, so the executable bit is not required by the runtime.

`bin/omarchy-hook-install`:

- copies a file to `~/.config/omarchy/hooks/<type>.d/<basename>`;
- forces mode `0755`.

Current documented events include `post-boot`, `post-update`, `pre-refresh-pacman`, `theme-set`, `font-set`, and `battery-low`. Blueprint must not use that list as an allowlist. It describes the current Omarchy release, not the portable profile grammar.

Upstream reference paths:

```text
omacom/omarchy:bin/omarchy-hook
omacom/omarchy:bin/omarchy-hook-install
omacom/omarchy:manual/31-dotfiles.md
omacom/omarchy:default/agents/skills/omarchy/hooks.md
```

## Goals

The milestone must:

1. add schema-5 profile state for Hooks;
2. discover every runtime-relevant user hook without recursively copying unrelated files;
3. capture exact hook bytes and desired permission modes;
4. represent an intentionally empty hook set;
5. produce semantic add/remove/content/mode drift;
6. restore missing or safely repairable hooks without overwriting unknown content;
7. preserve permission modes even when the profile is stored in Git;
8. reject path traversal, special files, invalid metadata, and corrupt snapshots; leave runtime entry symlinks unmanaged without following them;
9. mark every hook mutation high-risk;
10. never execute captured hook source during capture, restore, `check`, or verification;
11. integrate through the existing provider registry with no new provider-specific orchestration path.

## Non-goals

This milestone does not:

- execute hooks to test them;
- lint or shellcheck hook contents;
- remove extra target hooks;
- overwrite target hooks whose contents differ from the captured profile;
- infer whether a hook was written by the user or temporarily generated by Omarchy;
- scan hook source for secrets;
- support recursive arbitrary directories;
- add per-hook include/exclude policy;
- add rollback commands;
- add the TUI;
- add generic tracked-directory support.

Those are independent concerns and should not be coupled to the Hooks provider.

## Ownership model

The Hooks provider owns runtime-relevant files beneath:

```text
~/.config/omarchy/hooks
```

It does not claim ownership of every filesystem object beneath that root.

Runtime-relevant state is:

```text
<event>
<event>.d/<hook>
```

where the first form is a regular flat file and the second form is an immediate regular non-hidden, non-`*.sample` entry inside an event directory.

Directories not ending in `.d`, nested directories, hidden entries inside `.d`, and `*.sample` entries inside `.d` are outside the provider's desired-state model because current `omarchy-hook` does not execute them for a normal event invocation.

Runtime-relevant entry symlinks are never followed or captured. They are
reported as unmanaged external hooks and do not count as portable drift. A root
symlink remains an error because it escapes the provider boundary.

## Threat model

A hook is arbitrary shell source that Omarchy may execute automatically during system events such as boot, update, theme changes, font changes, and low-battery handling.

A profile may also be cloned from Git or received from another person. Therefore:

- hook source is untrusted executable code until the user approves restore;
- profile metadata must never choose an arbitrary destination path;
- restoring a hook must require the same source-integrity and destination-precondition protections as other Blueprint file mutations;
- Blueprint must not execute the hook as part of validation;
- a differing installed target hook is unknown user work and must not be overwritten;
- the CLI must display an explicit high-risk warning before approval.

### Mode representation

Profile mode is a four-character octal string:

```text
0000
0644
0755
```

Valid syntax is exactly `^[0-7]{4}$`, with a numeric value no greater than `0777`. Setuid, setgid, sticky, and other non-permission mode bits are outside this schema.

The string representation is intentional:

- it is readable in Git diffs;
- it does not rely on TOML integer formatting;
- Git does not reliably preserve arbitrary Unix permission bits in a working tree;
- `hooks.toml` therefore remains authoritative for desired permissions.

## Profile layout

```text
hooks/
├── hooks.toml
└── files/
    ├── post-boot
    ├── post-update.d/
    │   └── update-rust
    └── theme-set.d/
        └── retint-zellij
```

Example:

```toml
[[hook]]
path = "post-boot"
hash = "dddddddddddddddddddddddddddddddddddddddddddddddddddddddddddddddd"
mode = "0644"

[[hook]]
path = "post-update.d/update-rust"
hash = "4aaaaaaaaaaaaaaaaaaaaaaaaaaaaaaaaaaaaaaaaaaaaaaaaaaaaaaaaaaaaaaa"
mode = "0755"
```

Profile snapshots under `hooks/files/` are stored as regular mode-`0644` files regardless of the source hook's runtime mode.

This makes the profile copy inert and avoids relying on Git's executable-bit behavior. `hooks.toml` is authoritative for the mode that Blueprint applies at restore time.

## Path grammar

Profile hook paths are always slash-separated relative paths.

A valid path has exactly one of these forms:

```text
<event>
<event>.d/<filename>
```

### Flat form

A flat hook must:

- consist of exactly one non-empty path component;
- not be `.` or `..`;
- not contain `/`;
- not contain `\`;
- not be absolute.

A flat filename ending in `.sample` is not automatically excluded. Current Omarchy only applies the `.sample` exclusion inside the `.d/` scan.

A flat filename ending in `.d` is also valid when it is a regular file. Runtime behavior is determined by the filesystem object, not only by the suffix.

### Directory form

A directory-form hook such as `post-update.d/update-rust` must:

- contain exactly two components;
- have a first component ending in `.d`;
- have a non-empty event name before `.d`;
- have a non-empty second component;
- not use `.` or `..` as either component;
- not contain `\`;
- have a second component that does not begin with `.`;
- have a second component that does not end in `.sample`.

The hidden-file and `.sample` restrictions match current runtime behavior. No deeper path is valid.

### Canonical validation

Implement one canonical parser/validator and use it for captured metadata, profile `check`, snapshot destination derivation, and restore plan construction. Never construct a restore destination from unchecked profile path text.

`Raw` exists only in detected in-memory state. It is not persisted to TOML or emitted as a public profile field.

## Detection

`Provider.Detect()` reads live machine state.

### Hooks root

For `~/.config/omarchy/hooks`:

- missing root: return an empty state;
- symlink root: error;
- non-directory root: error;
- directory root: scan immediate entries.

Use `os.Lstat` for classification. Do not follow symlinks to decide they are safe.

### Root entries

For each immediate entry under the Hooks root:

- regular file: capture as a flat hook;
- symlink: record as unmanaged and continue;
- directory ending in `.d`: scan its immediate children;
- other directory: ignore;
- other special file: ignore because current `omarchy-hook` does not treat it as a regular hook file.

### `.d/` entries

For each immediate child of an event `.d/` directory:

1. if the name begins with `.`, ignore it;
2. if the name ends in `.sample`, ignore it;
3. regular file: capture;
4. symlink: record as unmanaged and continue;
5. directory: ignore and do not recurse;
6. special file: ignore.

The order matters: runtime-ignored dotfiles and samples should remain ignored rather than becoming profile errors merely because they are symlinks or other objects.

### Reading a hook

Use `content.OpenRegularFile` for every captured regular file.

Read the already-open file exactly once into `Raw`, then compute SHA-256 from those bytes. Do not hash and re-open the path separately.

Record:

```go
Path: canonical profile-relative path
Hash: SHA-256 of Raw
Mode: fmt.Sprintf("%04o", openedInfo.Mode().Perm())
Raw:  exact bytes read from the opened file
```

Reject source files whose `os.FileMode` contains setuid, setgid, sticky, or other unsupported special permission bits.

Sort detected hooks lexically by `Path`.

## Capture

`Provider.Capture(state State)` persists an already-detected state. It does not re-read live hook files.

Capture must:

1. validate every detected path and mode;
2. create a staging directory beneath `hooks/`;
3. write every `Raw` payload under staging `files/<Path>` as mode `0644`;
4. create metadata from `Path`, `Hash`, and `Mode`;
5. sort metadata lexically;
6. atomically replace the existing `hooks/files/` snapshot tree with the staged tree;
7. return `profile.Hooks`.

`profile.Save` writes `hooks/hooks.toml`.

An empty capture is intentional: `capture.hooks = true` with no `[[hook]]` entries. Re-capturing after hook deletion must remove stale snapshots.

## Capture-change summaries

Examples:

```text
+ hook post-update.d/update-rust
- hook battery-low.d/notify
~ hook theme-set.d/retint-zellij changed
~ hook post-boot mode 0644 → 0755
~ hook post-boot content and mode changed (0644 → 0755)
```

Use one change per hook path.

## Drift semantics

`Diff(saved, current)` is additive and path-based.

For every saved path:

- missing on machine: remove drift;
- same hash and same mode: no drift;
- different hash, same mode: modify drift;
- same hash, different mode: modify drift;
- different hash and mode: one combined modify drift.

For every current path absent from the saved profile, report additive drift.

Extra target hooks are drift but are not a verification failure and are never removed automatically.

## FileWrite mode extension

Hooks require explicit desired mode restoration.

Extend:

```go
type FileWrite struct {
    Source          string  `json:"source"`
    Destination     string  `json:"destination"`
    SourceHash      string  `json:"source_hash"`
    ExpectedHash    string  `json:"expected_hash,omitempty"`
    ExpectedMissing bool    `json:"expected_missing,omitempty"`
    Backup          bool    `json:"backup"`
    Mode            *uint32 `json:"mode,omitempty"`
    ExpectedMode    *uint32 `json:"expected_mode,omitempty"`
}
```

### Compatibility

For existing Config and Shell operations, `Mode == nil` and `ExpectedMode == nil` preserve current behavior exactly.

### Desired mode

When `Mode != nil`:

- reject values greater than `0777`;
- apply that mode to the temporary file before rename;
- do not use source snapshot mode;
- do not preserve destination mode.

When `Mode == nil`, preserve current behavior: new destinations use source mode and replacements preserve existing destination mode.

### Expected mode

When `ExpectedMode != nil` and the destination exists:

- compare `destinationInfo.Mode().Perm()` to the expected value;
- fail before mutation when it differs;
- repeat the same check at the final pre-rename validation boundary.

`ExpectedMode` must be nil when `ExpectedMissing` is true.

## Restore planning

Every hook mutation uses `model.RiskHigh`. No hook operation runs a command.

### Target missing

Plan an atomic `FileWrite` with `ExpectedMissing: true`, `Backup: false`, `SourceHash: saved.Hash`, and `Mode` set to the captured desired mode.

### Target already desired

When hash and mode both match, plan no operation.

### Mode-only drift

When content hash matches but mode differs, plan a `FileWrite` using:

- `ExpectedHash = current.Hash`;
- `ExpectedMode = current mode`;
- `Backup = true`;
- `Mode = desired mode`.

Blueprint rewrites the same bytes atomically and applies the captured mode. This avoids a separate chmod operation while retaining journaling and preconditions.

### Content differs

Do not overwrite. Append:

```text
skip hook:<path>
existing hook differs; overwrite disabled
```

Mode does not make differing content safe to replace.

### Extra target hook

Do not remove. Append:

```text
skip hook:<path>
additional hook left installed; removal disabled
```

### Target symlink or special file

An individual runtime symlink is unmanaged. Restore must never follow or
replace it; if it occupies a saved regular-hook path, restore skips that path.

## Backups and reversibility

For any replacement, including mode-only repair:

- `Backup = true`;
- the existing restore journal creates a backup before mutation;
- backup bytes and previous file permission bits are preserved;
- `BACKUP_CREATED` is recorded.

Missing-file creation has no backup. Automatic rollback remains out of scope.

## No execution on restore

Blueprint must never call `omarchy hook`, `bash <captured-hook>`, or `sh <captured-hook>` during capture, status, diff, restore, verification, or `check`.

A successful restore only changes files. The next real Omarchy event is what runs them.

## Verification

Verification is asymmetric. For every saved Hook, the path must exist in detected state and both hash and mode must match. Extra machine hooks do not fail verification.

Do not execute hooks to verify behavior.

## `check`

`Provider.Check(saved profile.Hooks)` validates profile integrity.

For every metadata entry:

- path passes canonical grammar;
- no duplicate path exists;
- hash is a valid lowercase SHA-256 hex digest;
- mode parses as exactly four octal digits in `0000..0777`;
- corresponding `hooks/files/<Path>` exists;
- snapshot is a regular non-symlink file;
- snapshot content hash equals metadata.

Also inspect the snapshot tree:

- reject symlinks and special files;
- reject orphan snapshot files not represented in `hooks.toml`;
- reject snapshot paths outside the canonical Hook grammar;
- an empty captured desired state must not contain stale snapshot files.

Profile loading separately enforces:

```text
capture.hooks = true
AND hooks/hooks.toml missing
→ invalid profile
```

## CLI risk UX

Any restore plan containing a Hooks mutation prints exactly one prominent warning:

```text
! Omarchy hooks are arbitrary user code that runs automatically on system events. Review captured hook source before approving this restore.
```

Hook progress uses the hook path, for example:

```text
Restoring hook post-update.d/update-rust...
✓ Restored hook post-update.d/update-rust
```

The plan continues to show each operation as `risk: high`.

## Secrets policy

Hooks are stored verbatim. Blueprint does not attempt hook-specific secret detection or redaction.

Documentation must warn:

> Hook source is stored verbatim in the profile. Hooks intended for version control should read credentials from environment variables, a password manager, or another external secret source rather than embedding secret values directly.

A regex-based secret scanner would produce false negatives and false confidence and should be designed as a cross-provider feature later.

## Error handling

Provider errors should identify the problematic relative path whenever possible.

Examples:

```text
detect hooks: hooks root is a symlink
capture hook post-boot: unsupported permission bits
check hooks: duplicate hook path "post-update.d/update-rust"
check hooks: snapshot hash mismatch for "theme-set.d/retint-zellij"
restore hooks: invalid profile hook path "../outside"
```

Capture should fail before saving profile metadata when detected runtime-relevant state cannot be represented safely. Restore should skip content conflicts, but malformed or corrupt profile state is a hard error.

## Testing strategy

### Path tests

Cover valid flat/unknown/`.d` paths, flat names ending `.d`, absolute traversal, `..`, nested paths, backslashes, empty event names, hidden `.d` children, `.sample` children, and mode parsing.

### Detection tests

Cover missing root, flat files, multiple `.d` hooks, unknown events, ignored samples/dotfiles/nested directories, non-`.d` directories, rejected root symlinks, unmanaged runtime symlinks, special permission bits, exact bytes, and mode retention.

### Capture/check tests

Cover exact bytes, inert snapshot mode `0644`, metadata mode, empty capture, stale removal, recapture deletion, duplicate metadata, invalid path/mode, missing/tampered/orphan snapshots, and snapshot symlink/special files.

### Diff/verify tests

Cover no drift, add, remove, content change, mode-only change, combined change, additive extras, and desired mismatch verification.

### Executor tests

Cover explicit mode on missing/existing files, nil-mode compatibility, expected-mode mismatch, final pre-rename mode validation, invalid desired mode, invalid expected-mode combination, and backup mode preservation.

### Restore plan tests

Cover missing hook write, no-op, mode-only repair, differing target skip, extra target skip, high-risk classification, and absence of command operations.

### App tests

Cover targeted and aggregate `capture`, `status`, `diff`, `restore`, and `check`, including an end-to-end exact-bytes-and-mode vertical slice and a conflict slice proving unknown target source is untouched.

## Acceptance criteria

The milestone is complete when all of the following hold:

1. Schema 1-4 profiles load as schema 5 with Hooks uncaptured.
2. Schema-5 captured Hooks require `hooks/hooks.toml`.
3. Empty Hooks capture is intentional and later additions appear as drift.
4. Flat hooks and direct `.d` hooks are captured.
5. Runtime-ignored `.sample`, dotfile, and nested `.d` content is not captured.
6. Unknown event names are portable without a Blueprint allowlist.
7. Runtime-relevant entry symlinks are unmanaged and never followed; root symlinks are rejected.
8. Captured source bytes are exact.
9. Profile snapshots are inert mode `0644`.
10. Desired runtime mode is represented in `hooks.toml`.
11. Git checkout mode behavior cannot change desired restored mode.
12. Content-only, mode-only, and combined drift are visible.
13. Missing desired hooks are safely created.
14. Mode-only drift is safely repaired.
15. Differing target source is never overwritten.
16. Extra target hooks are never removed.
17. Destination content and mode are both guarded at the final mutation boundary.
18. Existing files are backed up before replacement.
19. Every hook mutation is high-risk.
20. The CLI warns that hooks are arbitrary automatically executed code.
21. Blueprint never executes a hook during any provider operation.
22. Verification is additive and does not fail for extra hooks.
23. `check` catches malformed metadata, corrupt snapshots, stale/orphan files, symlinks, and special files.
24. Targeted and aggregate CLI flows work through the generic provider registry.
25. `go test ./...`, `go vet ./...`, and `go build ./cmd/omarchy-blueprint` pass on supported Go versions.

## Future work enabled by this milestone

The Hooks provider establishes reusable primitives for later work:

- explicit portable Unix file modes;
- expected-mode restore preconditions;
- safe capture of constrained file collections;
- high-risk executable-file UX;
- snapshot-tree integrity validation.

Those primitives can later support user-selected directories, scripts, small portable overlays, and other file-backed providers without making Hooks itself a generic directory feature.

# Documentation Comprehension & Consolidation Design

**Date:** 2026-09-14  
**Status:** Proposed implementation design  
**Baseline:** Prepared against PR #25 head `d66bf9f3e5c851aa309665733d96828dd5bb1a05`

## Goal

Make Omarchy Blueprint understandable before making its documentation exhaustive.

A new user should be able to understand what Blueprint is, how it fits normal Omarchy use, how capture/restore works, why restore is safe, and where to learn the TUI or CLI without reading architecture decisions or implementation details.

This is a documentation-only comprehension pass. It must not change product behavior, schemas, CLI semantics, capture/restore policy, or internal terminology.

## Current-state audit

The current README is doing too many jobs at once. It is roughly 19 KB and opens with implementation-level descriptions of Packages, Themes, Plugins, Config, Defaults, Shell, and bar-widget merge behavior before reaching the first workflow. The product idea is present, but it is buried beneath subsystem detail.

The current `docs/` tree does not yet provide a user-facing layer. It is primarily:

- architecture decision records under `docs/adr/`;
- `docs/manual-test-checklist.md` for maintainers;
- `docs/planning/` design and implementation planning material.

The TUI is now substantially clearer after PR #25, but the README still compresses startup, navigation, screen purpose, keybindings, Config behavior, Resources, Machines, Restore, and Sync into a dense section. It also still contains user-facing implementation vocabulary such as `provider`, `baseline`, and `drift`.

There is also a small consistency issue in `CONTRIBUTING.md`: it says to branch from `master`, while the active base branch is `main`.

## Product model the docs must teach

### The running system is the configuration editor

Users should configure Omarchy normally. Blueprint observes the meaningful user-controlled state and saves enough intent to reconstruct it elsewhere.

The primary mental model is:

```text
Use Omarchy normally
        ↓
Capture
        ↓
Portable, readable Blueprint profile
        ↓
Git / backup
        ↓
Fresh or different Omarchy machine
        ↓
Preview restore
        ↓
Approve restore
        ↓
Equivalent personalised environment
```

The profile is generated by Blueprint rather than manually authored, while remaining human-readable and Git-friendly.

### Prefer reconstruction over snapshots

When possible, Blueprint should reconstruct from the most authoritative source rather than copy bytes unnecessarily:

1. Native Omarchy operation
2. Native package manager
3. Authoritative remote source
4. Captured profile content
5. Manual action when safe automation is unavailable

This explains why Packages, built-in themes/plugins, Git-backed Resources, and copied local content behave differently without forcing users to learn provider internals.

### Safety is a workflow, not a footnote

The user-facing restore story should be:

```text
inspect → calculate → preview → approve → apply → verify
```

Docs should emphasize that Blueprint does not silently delete additional packages, blindly snapshot the machine, capture secrets on purpose, or overwrite conflicts simply because a profile contains a desired value.

### State, policy, and restore intent are different

Documentation must preserve the distinction between:

- **State:** what Blueprint observed;
- **Policy:** whether Blueprint should manage something;
- **Restore intent:** what a selected restore plan would actually do.

Do not collapse these concepts into a single “managed/unmanaged” explanation.

## Documentation strategy

### Approaches considered

#### A. Rewrite only `README.md`

**Pros:** Smallest diff; easy to review.  
**Cons:** Leaves the same structural problem: the README must either stay too long or omit useful guidance entirely. TUI, CLI, and Resources remain homeless.

#### B. Compact README plus a small user-guide layer — **recommended**

Keep `README.md` as the landing page and add a handful of focused Markdown guides under `docs/`. Existing ADRs and maintainer docs remain intact.

**Pros:** Clear audience boundaries; small enough to maintain; no docs framework; lets README become concise without losing useful material.  
**Cons:** Requires maintaining links between a few files.

#### C. Full documentation site / generated reference

**Pros:** Best long-term navigation and search.  
**Cons:** Adds tooling and maintenance before the product needs it; creates scope far beyond this consolidation pass.

### Decision

Use **Approach B**.

## Target information architecture

```text
README.md                         # landing page + quickest successful workflow
CONTRIBUTING.md                   # contributor setup / verification

docs/
  README.md                       # documentation index by audience
  guide.md                        # mental model, lifecycle, categories, safety, profile
  tui.md                          # interactive workflow and screen purposes
  cli.md                          # common CLI workflows and automation conventions
  resources.md                    # explicit files/folders/Git resources + machine paths
  manual-test-checklist.md        # maintainer acceptance checklist (existing)
  adr/                            # architecture decisions (existing)
  superpowers/                    # design / implementation history (existing)
```

No documentation generator or site framework is introduced.

## File responsibilities

### `README.md` — landing page

The README should answer, in order:

1. **What is Omarchy Blueprint?**
2. **What problem does it solve?**
3. **How do I try it?**
4. **What does it remember?**
5. **Is restore safe?**
6. **Should I use the TUI or CLI?**
7. **Where do I read more?**
8. **What are the requirements / how do I build it?**

Target structure:

```markdown
# Omarchy Blueprint
<tagline>

## What Blueprint does
## Quick start
## How it works
## What Blueprint can remember
## Safety model
## TUI and CLI
## Documentation
## Requirements
## Build and test
## Project status
```

The quick-start workflow should appear near the top, not after subsystem internals.

The README should be roughly half its current size; target **10 KB or less** without gaming the target by duplicating the removed prose elsewhere verbatim.

It should not contain exhaustive subsystem behavior, long safety edge-case lists, the full profile tree, repeated category-specific command examples, Resources strategy detail, or machine mapping detail.

### `docs/README.md` — documentation index

This is the audience router.

Suggested structure:

```markdown
# Omarchy Blueprint documentation

## Start here
- Guide
- TUI
- CLI
- Resources

## Project and contributor reference
- ROADMAP
- Architecture decisions
- Manual test checklist
- Contributing
```

Do not promote `docs/planning/` as user documentation. It can remain in the repository as implementation history.

### `docs/guide.md` — how Blueprint thinks

This guide should explain the product, not the implementation.

Required sections:

1. **The running system is the configuration editor**
2. **Capture → profile → restore**
3. **Reconstruction before copied bytes**
4. **What Blueprint remembers**
5. **Portable vs machine-specific state**
6. **State, policy, and restore intent**
7. **Profiles are readable and Git-friendly**
8. **Safety model**
9. **Current boundaries**

“What Blueprint remembers” should use user-facing category names:

- Packages
- Themes
- Plugins
- Defaults
- Config
- Shell
- Hooks
- Resources

Machines should be explained as per-machine placement for Resources, not as another captured content category. Sync should be described as profile Git workflow, not application-state capture.

The profile layout may be shown here in a short representative tree, but it should not become a format specification.

### `docs/tui.md` — interactive use

The TUI guide should use the shipped screen catalogue as the wording source of truth rather than creating parallel descriptions.

Required sections:

1. **Launching the TUI**
2. **How navigation works**
3. **Command palette and searchable help**
4. **Workflow screens** — Overview, Capture, Restore
5. **Software screens** — Packages, Themes, Plugins, Defaults
6. **Customisation screens** — Config, Shell, Hooks, Resources
7. **Profile screens** — Machines, Sync
8. **Config states and policies**
9. **Compact terminals and `NO_COLOR`**

Do not create a giant static keybinding table. The footer and `?` help are contextual and should remain the canonical detailed key reference.

The guide may document stable navigation primitives such as `j`/`k`, `Tab`, `:`, `?`, and `[`/`]`, but should tell users to use `?` for screen-specific actions.

#### Config policy wording

Use the exact user-facing meanings:

- **Auto** — “Blueprint decides based on Omarchy defaults, ownership, and safety rules.”
- **Included** — “You asked Config to manage this path when it is safe to do so.”
- **Excluded** — “You asked Config to leave this path alone.”

Also state explicitly: **Included never overrides safety rules.**

#### Config groups

Use the shipped group labels:

- Needs review
- Changes
- No action needed
- Not managed by Config

Do not document internal classification enum names as the main user vocabulary.

### `docs/cli.md` — common CLI workflows

This is a workflow guide, not a generated command reference.

Start with a note that `omarchy-blueprint --help` and subcommand help are canonical for complete flags/options.

Required sections:

1. **Create or select a profile**
2. **Capture**
3. **Check / status / diff**
4. **Preview and apply restore**
5. **Target one category**
6. **Include / exclude policy examples**
7. **Profile Git workflow**
8. **Non-interactive and JSON use**
9. **Exit codes**

Keep command examples representative. Avoid five nearly identical capture/status/restore blocks for Themes, Config, Defaults, Shell, and Hooks.

Use “category” in prose. Internal names or literal command syntax remain unchanged.

### `docs/resources.md` — explicit portable resources

Move the specialized Resources material out of README and make it coherent in one place.

Required sections:

1. **When to use Resources**
2. **Track / untrack**
3. **Strategy: `git`**
4. **Strategy: `git+diff`**
5. **Strategy: `copy`**
6. **Symlink adoption**
7. **Conflicts and additive restore**
8. **Machine-specific Resource paths**
9. **Safety boundaries**

This file should preserve the useful operational detail currently in README, but rewrite it as an intentional guide rather than a pasted feature log.

### `CONTRIBUTING.md`

Change “branch from `master`” to “branch from `main`”. Keep the rest of this PR focused; do not turn the docs comprehension pass into a contributor-guide rewrite.

## Terminology rules

These apply to **new user-facing prose** in `README.md`, `docs/README.md`, `docs/guide.md`, `docs/tui.md`, `docs/cli.md`, and `docs/resources.md`.

| Internal / older presentation | User-facing wording |
| --- | --- |
| provider | category / feature / screen, depending on sentence |
| baseline | Omarchy default |
| drift | differences |
| Git theme | installed theme |
| Git plugin | installed plugin |
| managed provider lifecycle | capture / compare / restore workflow |

Do **not** mechanically rename:

- Go types, package names, JSON/TOML fields, stored profile fields;
- literal CLI syntax;
- historical ADR text;
- error/output text that is intentionally quoted from the program.

If technical terminology must appear, introduce it after the user concept rather than making it the first explanation.

## Writing style

- Lead with user intent, then explain mechanism.
- Prefer short paragraphs and concrete examples.
- Explain the common workflow before edge cases.
- Use tables only when they clarify categories or terminology.
- Avoid release-note phrasing such as “this repository currently contains…” in evergreen user docs.
- Avoid presenting implementation constraints as the product definition.
- Do not promise behavior that the current code does not provide.
- When safety has an exception or limitation, state it next to the action it affects.

## Non-goals

This PR must not:

- change Go code or TUI behavior;
- change profile schemas or migration rules;
- rename internal provider/domain identifiers;
- rename CLI commands or flags;
- redesign capture/restore policy;
- add a documentation website, generator, or new dependency;
- rewrite ROADMAP or historical ADRs;
- perform the planned TUI internal consolidation;
- add onboarding product behavior.

Those remain separate follow-up work.

## Acceptance criteria

### README

- A new reader sees the product mental model before subsystem detail.
- Quick start appears near the top.
- README is approximately half the current size, with a target of 10 KB or less.
- README contains no long Resources/Machines reference sections or repeated per-category workflows.
- TUI and CLI each have a short introduction and links to their guides.

### User docs

- `docs/README.md`, `docs/guide.md`, `docs/tui.md`, `docs/cli.md`, and `docs/resources.md` exist and have distinct responsibilities.
- The TUI guide matches the current screen catalogue and Config presentation copy.
- The CLI guide explicitly says `--help` is canonical for exhaustive flags.
- Resources strategies and machine path mappings remain documented after leaving README.

### Language

- New user-facing prose uses category, Omarchy default, differences, installed theme, and installed plugin terminology.
- Config policy explanations use the approved copy.
- Included is never described as bypassing safety.

### Scope

- No Go/source/schema behavior changes.
- ROADMAP, ADRs, manual test checklist, and existing internal planning history are not rewritten for presentation terminology.
- `CONTRIBUTING.md` refers to `main`, not `master`.

### Verification

- All relative Markdown links resolve.
- `git diff --check` is clean.
- Existing repository verification still passes (`go test ./...`, `go vet ./...`, `go build ./cmd/omarchy-blueprint`).
- A reviewer can answer these questions from README + linked user docs without reading ROADMAP or ADRs:
  1. What is Blueprint?
  2. What should I do after changing my Omarchy setup?
  3. What is saved versus reconstructed?
  4. What happens before restore mutates anything?
  5. Where do I learn the TUI, CLI, or Resources workflow?

## Review guidance

Review this PR primarily as a comprehension change, not as a copy-editing exercise.

Reject changes that are individually accurate but recreate the current failure mode: long implementation-first explanations, duplicate reference material, or terminology that makes users understand the architecture before they understand the product.

# Guide

This guide explains how Omarchy Blueprint thinks about your system, not how
it is implemented. For interactive use see the [TUI guide](tui.md); for
scripted use see the [CLI guide](cli.md); for explicitly tracked files and
projects see the [Resources guide](resources.md).

## The running system is the configuration editor

You do not maintain a separate declarative file that describes your Omarchy
setup. You install packages, pick a theme, enable plugins, customise the
shell, and edit config the normal way. Blueprint observes that system and
saves the meaningful choices it finds, so the machine you are already using
is the source of truth.

## From system to profile to another machine

```text
Use Omarchy normally
        ↓
Capture
        ↓
Portable Blueprint profile
        ↓
Git / backup
        ↓
Another Omarchy machine
        ↓
Preview and approve restore
        ↓
Equivalent personalised environment
```

Capture reads your current setup and writes what it finds into a profile —
a directory of readable files. That profile can be committed to Git, backed
up, and cloned onto a fresh or different Omarchy machine, where restore
previews and then applies the changes needed to reach an equivalent
personalised environment.

Blueprint captures your intent rather than requiring you to hand-author a
declarative system configuration up front.

## Reconstruct first, copy only when needed

When Blueprint can rebuild something from an authoritative source, it
prefers that over copying bytes. In order of preference:

1. Native Omarchy operation
2. Native package manager
3. Authoritative remote source
4. Captured profile content
5. Manual action, when no safe automation is available

This is why an installed theme or plugin with a clean Git origin is restored
by re-fetching that origin, while a package is restored by reinstalling it
rather than copying binaries, and only genuinely local or modified content is
copied into the profile itself.

## What Blueprint remembers

Blueprint organizes what it remembers into a small set of categories:

- **Packages** — explicitly installed system and AUR packages, plus global Mise tool declarations.
- **Themes** — your selected theme and the themes saved in your profile.
- **Plugins** — Omarchy plugin code and sources Blueprint can reconstruct.
- **Defaults** — your chosen default terminal, browser, editor, and agent.
- **Config** — dotfiles and other application/system configuration, mainly under `~/.config`.
- **Shell** — your customised Omarchy shell, bar, and layout state.
- **Hooks** — scripts Omarchy runs automatically at supported hook points.
- **Resources** — files, folders, and Git projects you explicitly asked Blueprint to carry.

Two more concepts sit alongside these categories rather than inside them:
**Machines** control where a Resource is placed on a particular computer, and
**Sync** manages the Git repository that holds your Blueprint profile. Neither
one captures application state on its own.

## Portable and machine-specific state

Not everything belongs on every machine. Blueprint separates state it
expects to work anywhere (a portable package, a theme, a shell
customisation) from state that is tied to one computer, such as a
hardware-specific driver package or a Resource placed at a different path on
a particular machine. Portable state is what restore reproduces by default;
machine-specific state is remembered without being forced onto machines it
does not belong on.

## State, policy, and restore intent

These three ideas are related but distinct, and Blueprint keeps them
separate rather than collapsing them into a single "managed" flag:

- **State** is what Blueprint observed on this machine.
- **Policy** is whether Blueprint should manage a given item or path at all.
- **Restore intent** is what a selected restore plan would actually do.

A path can differ from your profile (state), be included, excluded, or left
to Blueprint's judgement (policy), and still result in no change, a
conflict, or a safe update once a specific restore plan is calculated
(restore intent).

## Profiles are readable and Git-friendly

A Blueprint profile is a directory of plain files:

```text
profile.toml
packages/
themes/
plugins/
config/
defaults/
shell/
hooks/
resources/
```

Each category owns its own files inside the profile, in formats meant to be
readable and diffable rather than opaque. The profile is generated by
Blueprint, not primarily hand-authored, but nothing stops you from reading it
or reviewing changes to it like any other Git-tracked project.

## Safety model

Restoring onto a machine is a workflow, not a single mutating step:

```text
inspect → calculate → preview → approve → apply → verify
```

Blueprint calculates a plan, shows it to you before anything changes, and
only applies it once you approve — interactively or with an explicit
non-interactive confirmation. A few guarantees hold across categories:

- Blueprint does not silently delete packages beyond what your profile expects.
- Blueprint does not blindly snapshot the whole machine; it captures specific, meaningful categories.
- Blueprint does not intentionally capture secrets into the profile.
- Blueprint does not overwrite a conflict just because the profile has a different desired value.

See the [TUI guide](tui.md) and [CLI guide](cli.md) for how preview and
approval actually look in each interface.

## Current boundaries

Blueprint does not yet distinguish packages you added yourself from other
explicitly installed packages, so removal of extra packages stays disabled
rather than guessed at. Theme, plugin, and config restore favor leaving a
conflicting target alone over overwriting it. Defaults restore never unsets
a machine-selected default. Broader machine-specific state, a generic backup
feature, advanced Git workflows, and agent-assisted migration remain future
work rather than current behavior.

# Omarchy State

## Portable, version-controlled system profiles for Omarchy

**Status:** Working specification
**Project name:** `omarchy-state`
**Initial form:** CLI + TUI
**Future form:** Omarchy Shell plugin
**Target:** Omarchy 4+

---

# 1. Summary

Omarchy State is a tool for capturing the meaningful user-controlled state of an Omarchy installation into a portable, human-readable profile that can be version-controlled and restored onto another machine.

The goal is to provide much of the reproducibility of NixOS/Home Manager without requiring the user to maintain a large declarative configuration.

Instead:

> **The running system is the configuration editor.**

The user installs packages, changes keybindings, adds themes, configures the shell, installs plugins and otherwise uses Omarchy normally.

Omarchy State observes that system and produces a portable representation of those choices.

```text id="p1v8hj"
Normal Omarchy usage
        ↓
Capture
        ↓
Portable state profile
        ↓
Git / backup
        ↓
Fresh Omarchy installation
        ↓
Restore
        ↓
Equivalent personalised environment
```

The profile is generated by the tool rather than authored manually, although it remains readable and editable.

---

# 2. Goals

Omarchy State should make it possible to:

- reproduce a personalised Omarchy installation on another machine;
- version-control system customisation;
- selectively capture and restore individual categories or items;
- distinguish portable configuration from machine-specific configuration;
- capture selected user files and directories where useful;
- reconstruct Git-backed resources from their authoritative source rather than unnecessarily copying them;
- preview exactly what a capture or restore will change;
- detect drift between a machine and its saved profile;
- survive Omarchy upgrades through version-aware migrations;
- use existing Omarchy commands wherever possible rather than modifying state directly;
- optionally use the user's configured Omarchy agent to explain changes, generate commit descriptions and assist migrations;
- never require an AI agent for core functionality;
- avoid capturing secrets by default.

The user experience should feel substantially simpler than Nix, Ansible or manually maintaining a large dotfiles repository.

---

# 3. Non-goals

Version 1 will not attempt to:

- image or snapshot the entire filesystem;
- become a general-purpose personal backup solution;
- back up large document, photo or media libraries;
- reproduce every possible Linux system modification;
- become a replacement package manager;
- replace Snapper or Omarchy's rollback mechanisms;
- automatically upload secrets;
- guarantee bit-for-bit identical machines;
- silently delete data during restore;
- execute arbitrary AI-generated migrations without explicit approval.

This is primarily a **system personalisation and reconstruction tool**, not a disk backup system.

# 4. Product principles

## 4.1 Capture state rather than author state

The primary workflow is:

```bash id="w81e67"
omarchy-state capture
```

not:

```bash id="n08avg"
vim massive-config.toml
```

Users should configure Omarchy normally.

---

## 4.2 Semantic state over raw files

Whenever possible, state should be represented as:

```text id="7i6awj"
Installed package: ghostty
Enabled plugin: acme.weather
Default browser: chromium
Theme: catppuccin
Tracked project: github.com/user/project
```

rather than only:

```text id="bv2so8"
~/.config/foo/bar.conf changed
```

Raw files remain necessary in some cases, but semantic state produces safer restores and better diffs.

---

## 4.3 Capture intent and provenance before bytes

Where something can be recreated from an authoritative source, Omarchy State should record how to reconstruct it instead of duplicating the underlying data.

Preferred reconstruction order:

```text id="8iu58z"
1. Native Omarchy operation
2. Native package manager
3. Authoritative remote source
4. Captured profile content
5. Manual / assisted reconstruction
```

Examples:

```text id="f85d9k"
ghostty
→ package
→ pacman / Omarchy package command

weather plugin
→ plugin
→ Git source

Catppuccin theme
→ theme
→ Git source

~/Projects/website
→ tracked directory
→ Git clone

~/.local/bin
→ tracked directory
→ captured files
```

This keeps profiles smaller, clearer and easier to migrate.

---

## 4.4 Selectivity is a first-class feature

Users must be able to include or exclude:

- entire state categories;
- individual packages;
- individual themes;
- individual plugins;
- individual config files;
- individual tracked directories;
- individual Git repositories;
- machine-specific settings.

Capture and restore should both support this.

---

## 4.5 Safe by default

Operations should follow:

```text id="dqold7"
inspect
→ calculate
→ preview
→ approve
→ apply
→ verify
```

Destructive replacement should never be the default behaviour.

---

## 4.6 Omarchy-native where possible

If Omarchy exposes an operation such as:

```bash id="ybq7ia"
omarchy plugin add
omarchy plugin enable
omarchy default ...
omarchy pkg add
```

that interface should be preferred over directly mutating the underlying implementation.

Omarchy State should complement Omarchy rather than create a parallel configuration system.

---

# 5. Core concepts

## 5.1 Profile

A profile is a portable representation of desired machine state.

Example:

```text id="ynvuxo"
~/.local/share/omarchy-state/profiles/main/

profile.toml
packages/
themes/
plugins/
config/
hooks/
directories/
machines/
migrations/
metadata/
```

Profiles may optionally be Git repositories.

---

## 5.2 Provider

Each category of state is implemented by a provider.

Providers implement a common contract:

```text id="vm602d"
detect()
capture()
diff()
plan_restore()
restore()
verify()
```

Initial and future providers may include:

```text id="dzhpgn"
packages
themes
plugins
shell
hyprland
hooks
defaults
directories
fonts
services
webapps
system-config
```

This architecture allows the core engine to remain stable as support expands.

---

## 5.3 Portable vs machine-specific state

Every captured item should optionally have a portability classification:

```text id="kpi4di"
portable
machine-specific
sensitive
ignored
```

Examples:

```text id="ehkp4y"
keybindings           portable
installed packages    portable
theme                 portable
projects directory    portable
monitor layout        machine-specific
NVIDIA settings       machine-specific
SSH private keys      sensitive
browser cache         ignored
```

---

## 5.4 Resource ownership

Every managed resource should have one primary provider responsible for restoring it.

For example:

```text id="u7wldq"
plugins provider
    owns plugin installation/provenance

shell provider
    owns shell layout and plugin placement
```

A generic tracked-directory provider should not silently duplicate state already owned by another provider.

If a user tries to track:

```text id="eqnkzo"
~/.config/omarchy
```

the tool should warn that portions are already managed semantically.

# 8. Capture workflow

Primary command:

```bash id="bdr1gy"
omarchy-state capture
```

Stage 1 — inspect the machine.

Stage 2 — compare current system state to the saved profile.

Stage 3 — display semantic changes.

Example:

```text id="z3xzqn"
Changes detected

Packages
  + ghostty
  + lazydocker
  - alacritty

Themes
  + catppuccin
  ~ current: tokyo-night → catppuccin

Plugins
  + acme.weather
  ~ clock plugin modified locally

Keybindings
  ~ 3 bindings changed

Shell
  ~ bar position: top → bottom

Directories
  + project: omarchy-state
  ~ ~/.local/bin/deploy

Machine-specific
  ~ monitor layout changed
```

The user may select exactly what to capture:

```text id="xwjoxb"
[x] Packages
    [x] ghostty
    [x] lazydocker
    [ ] remove alacritty

[x] Themes
    [x] catppuccin
    [x] active theme

[x] Plugins
    [x] acme.weather
    [ ] local clock modifications

[x] Keybindings

[x] Directories
    [x] ~/Projects/omarchy-state
    [x] ~/.local/bin/deploy

[ ] Monitor layout
```

Then:

```text id="6pmzdg"
Capture 8 changes? [Y/n]
```


# 16. Packages provider

The packages provider should distinguish:

```text id="5ybkcr"
official repository package
AUR / foreign package
dependency
explicit installation
```

Only explicitly installed packages should normally be captured.

Stored representation:

```text id="iamdpd"
packages/official.txt
packages/aur.txt
```

Example:

```text id="p46e31"
ghostty
docker
docker-compose
neovim
```

Provider responsibilities:

```text id="2f8mq5"
detect installed packages
determine explicit packages
classify repository/AUR
compare against profile
install missing packages
optionally remove extras
verify result
```

Removing additional packages should be off by default.

---

# 17. Themes provider

Themes should be classified as:

```text id="dtbi66"
Omarchy built-in
Git-installed
local/custom
```

Example metadata:

```toml id="fh24dj"
[[theme]]
id = "catppuccin"
type = "git"
url = "https://github.com/example/catppuccin-omarchy"
revision = "a914ae3"
enabled = true
```

Custom themes should be copied into:

```text id="3cnk1b"
themes/local/
```

The capture UI should support selecting individual themes.

---

# 18. Plugins provider

Third-party plugins should be captured semantically wherever possible.

Example:

```toml id="3if2ur"
[[plugin]]
id = "acme.weather"
source = "git"
url = "https://github.com/acme/omarchy-weather.git"
revision = "91af712"
enabled = true
```

For a locally modified or custom plugin:

```toml id="00d7wy"
[[plugin]]
id = "sam.clock"
source = "local"
path = "plugins/local/sam.clock"
enabled = true
```

Restore should use native Omarchy plugin operations where possible.

Third-party plugin security prompts should be respected during interactive restore.

---

# 19. Shell provider

The shell provider should understand semantic fields inside Omarchy's shell configuration rather than treating it exclusively as an opaque file.

Possible state:

```text id="r0lhpu"
bar
bar position
widget layout
widget settings
idle configuration
disabled first-party plugins
enabled third-party plugins
```

This enables diffs such as:

```text id="l9y3or"
Bar
  position: top → bottom

Widgets
  + weather
  workspaces: left[1] → left[0]

Idle
  lock: 300s → 600s
```

instead of a large JSON diff.

# 21. User-selected directories

Users may optionally add arbitrary files or directories to their profile.

Examples:

```bash id="joqtp9"
omarchy-state track ~/Projects
omarchy-state track ~/Scripts
omarchy-state track ~/.local/bin
omarchy-state track ~/.config/special-app
```

Files should also be valid resources.

```bash id="otbafj"
omarchy-state track ~/.gitconfig-work
```

These resources participate in:

```text id="t0s2v4"
capture
status
diff
restore
check
```

The generic directories provider should only manage paths not already owned by a more specific provider unless the user explicitly overrides that protection.

# 22. Directory reconstruction strategies

Tracked paths can use one of several strategies:

```text id="slb8mc"
auto
copy
git
mixed
reference
ignore
```

## `copy`

Store selected contents in the profile.

Useful for:

```text id="2esh1t"
~/.local/bin
~/Scripts
small local configs
non-generated files
```

Example:

```toml id="agcivx"
[[directory]]
id = "scripts"
path = "~/.local/bin"
mode = "copy"
```

---

## `git`

Record enough Git metadata to reconstruct the repository instead of storing its entire contents.

Example:

```toml id="nfz3sc"
[[directory]]
id = "state-project"
path = "~/Projects/omarchy-state"
mode = "git"

remote = "git@github.com:user/omarchy-state.git"
branch = "main"
revision = "4f31d80"
```

Restore:

```text id="hbsx99"
create parent directory
→ clone remote
→ checkout desired state
→ restore approved local changes
→ verify
```

---

## `mixed`

Recursively inspect a broader directory.

Example:

```text id="464mwe"
~/Projects
├── website/        Git repository
├── api/            Git repository
├── experiments/    ordinary files
└── notes.md        ordinary file
```

Git repositories are reconstructed from Git.

Other selected content is copied.

This should be useful for directories such as:

```text id="nre8kh"
~/Projects
~/Code
~/Development
```

---

## `reference`

Record the path and descriptive metadata without storing its contents.

Useful for externally managed resources.

---

## `ignore`

Explicitly mark a path as unmanaged.

---

## `auto`

Inspect the directory and recommend a strategy rather than silently choosing one.

For example:

```text id="snfi6b"
Git repo            → recommend git
small local dir     → recommend copy
mixed project tree  → recommend mixed
large generated dir → recommend exclusion
sensitive path      → warning/refusal
```

---

# 23. Git-aware directory handling

For detected Git repositories, inspect:

```text id="wetqdc"
repository root
remote URLs
current branch
HEAD revision
detached HEAD
working-tree state
uncommitted tracked changes
untracked files
ignored files
submodules
Git LFS
```

A clean repository may require only:

```toml id="g1r7ab"
[[git_repo]]
directory = "projects"
relative_path = "website"

remote = "git@github.com:user/website.git"
branch = "main"
revision = "f902cb1"
restore_policy = "branch"
```

# 24. Git restore policy

Users should be able to choose between:

```text id="jdlkme"
follow branch
pin revision
```

Example:

```toml id="x7qttp"
restore_policy = "branch"
branch = "main"
```

or:

```toml id="qdqo82"
restore_policy = "revision"
revision = "f902cb1"
```

Following a branch is useful for active projects.

Pinning a revision is useful for stronger reproducibility.

---

# 25. Dirty Git repositories

If a repository contains local work:

```text id="wbrvjv"
4 modified files
2 untracked files
```

the capture UI should offer:

```text id="nvlv5x"
● Clone repository + preserve local changes
○ Clone repository only
○ Store entire directory
○ Ignore
```

Omarchy State must never automatically push or commit local work.

---

# 26. Preserving local Git state

Tracked modifications can be stored as a patch.

Untracked files may be copied separately if explicitly included.

Example:

```text id="87759t"
directories/
└── git-state/
    └── projects-website/
        ├── metadata.toml
        ├── tracked.patch
        └── untracked/
```

Restore:

```text id="a6gtyc"
clone repository
→ checkout branch/revision
→ apply patch
→ restore selected untracked files
→ verify
```

If the patch no longer applies cleanly, create a conflict rather than forcing it.

Ignored files remain excluded by default.

---

# 27. Directory exclusions

Tracked directories should support exclusions.

Example:

```toml id="4dosb1"
[[directory]]
id = "projects"
path = "~/Projects"
mode = "mixed"

exclude = [
    "**/node_modules",
    "**/.venv",
    "**/target",
    "**/dist",
    "**/__pycache__"
]
```

Omarchy State may suggest common generated directories but should not silently exclude unfamiliar content.

# 28. Storage estimation

Before capturing a large directory, estimate profile impact.

Example:

```text id="88fsvm"
~/Projects/experiments

Files: 14,281
Size: 7.3 GB

Detected:

  node_modules    5.1 GB
  .venv           1.4 GB
  cache           320 MB
  source files    480 MB

Suggested capture size:
  486 MB
```

Large files should also trigger warnings.

# 29. Directory path aliases

Tracked paths should have stable logical IDs.

Example:

```toml id="23neab"
[[directory]]
id = "projects"
path = "~/Projects"
mode = "mixed"
```

Internally, providers refer to:

```text id="niq0wc"
directory:projects
```

rather than hardcoding the source path.

This enables portable remapping.

# 30. Restore path mappings

A profile should not assume identical filesystem layouts on every machine.

Example:

```text id="rccph6"
profile:
projects → ~/Projects

laptop:
projects → ~/Code
```

Machine overlay:

```toml id="973nc3"
[paths]
projects = "~/Code"
scripts = "~/bin"
```

Interactive restore may also offer:

```text id="rr77mf"
Profile path:
  ~/Projects

Restore to:

● ~/Projects
○ ~/Code
○ Custom...
```

# 31. Restore collisions

If the destination already exists, inspect it first.

For Git repositories:

```text id="8p33v7"
~/Projects/website already exists

Expected remote:
github.com/user/website

Found remote:
github.com/user/website

Current branch:
feature/navbar

Working tree:
dirty
```

Possible actions:

```text id="w6sgtq"
● Leave untouched
○ Update compatible repository
○ Apply saved local state only
○ Replace repository
○ View details
```

Replacement requires explicit confirmation.

For copied directories, unknown destination files should not be deleted by default.

# 32. Machine profiles

Example:

```text id="m6pud9"
├── portable state
├── desktop overlay
└── laptop overlay
```


# 33. Git integration

```text id="510psi"

8 changes:
+ 2 packages
+ 1 theme
+ 1 plugin
+ 1 project
~ 3 configs

Commit these changes? [Y/n]
```

Default deterministic commit:


```text id="41vfja"

```

Git-related commands:


Omarchy State should not attempt to replace Git.

# 34. Optional agent integration

Agent features should use **Omarchy's configured default agent** rather than integrating individual AI providers.

Core functionality must never require an agent.

Configuration:

```toml id="15yeit"
[agent]
enabled = false

descriptions = "ask"
migrations = "ask"
conflict_resolution = "ask"
```

Possible interactive setup:

```text id="3pkhgz"
Use your Omarchy default agent for:

[x] Capture summaries
[x] Git commit descriptions
[ ] Restore explanations
[ ] Migration suggestions
[ ] Conflict resolution
```

```json id="ahlp7u"
  ]
}
```

The configured agent can be asked to turn this into a concise summary or commit description.

The user sees the result before it is used.

# 36. Agent-assisted migrations

Deterministic migrations remain preferred.

Example:

```text id="yhsuhz"
profile schema 3
       ↓
known migration
       ↓
profile schema 4
```

For difficult user-modified configuration:

```text id="kwxw98"
old Omarchy default
user's old config
new Omarchy default
migration notes
```

may be supplied to the configured agent.

The agent produces a proposed patch.

Workflow:

```text id="5r7r5n"
migration required
      ↓
deterministic migration?
      ├─ yes → generate patch
      └─ no
          ↓
      agent assistance enabled?
          ├─ no → manual conflict
          └─ yes
               ↓
           proposed patch
               ↓
             diff
               ↓
         user approval
               ↓
             apply
```

The agent must not silently apply migrations.

---

# 37. Agent-assisted conflict resolution

The same mechanism may later help with:

- failed three-way config merges;
- Git working-tree patch conflicts;
- changed configuration syntax;
- deprecated Omarchy plugin APIs.

For example:

```text id="0e8eu0"
Saved local changes no longer apply cleanly to:

~/Projects/website/src/header.tsx
```

The agent may propose a patch.

The user must review and approve it.

# 38. AI security model

Agent usage should have explicit capability levels.

## Level 0 — disabled

No agent usage.

## Level 1 — describe

Agent receives structured, preferably redacted diff information.

Can produce:

```text id="hlkmve"
capture summary
commit message
human explanation
```

Cannot modify files.

## Level 2 — propose

Agent may receive selected configuration content and generate a patch.

The patch is displayed.

Cannot apply it itself.

## Level 3 — execute

Potential future feature only.

Not part of the initial roadmap.

Before sending content to an agent or adding it to a profile, run sensitivity checks.

Potential secrets include:

```text id="ap1xrv"

passwords

browser profiles
secret stores
```

Known sensitive paths should include patterns such as:

```text id="79coju"

~/.aws/credentials
.env

*token*
*secret*
*password*
```

Potentially sensitive content should be:

```text id="dqiu7r"

or require explicit approval
```

Ignored Git files should not be captured by default, which also reduces accidental secret inclusion.

# 40. Migration system

Profiles should have their own schema version:

```toml id="59uoha"
schema = 3
```

and record the Omarchy version from capture:

```toml id="z6gn6c"
[omarchy]
captured_version = "4.2.1"
```

There are two migration classes.

## Profile migrations

Changes to Omarchy State's own storage format.

```text id="3ltlav"
schema 1 → 2
schema 2 → 3
```

These should be deterministic.

## Omarchy migrations

Changes required because Omarchy configuration semantics changed.

Example:

```text id="p5z9fw"
Omarchy 4.1 shell config
        ↓
Omarchy 4.4 shell config
```

These may combine:

```text id="oc7ijq"
known migration rules
three-way merge
agent-generated proposal
manual conflict resolution
```

# 41. Three-way configuration migration

Where useful, preserve enough metadata to identify the upstream state from which a user configuration was derived.

Conceptually:

```text id="5peh1k"
A = old Omarchy default
B = user's modified configuration
C = new Omarchy default
```

Restore attempts:

```text id="m7p7go"
merge(A, B, C)
```

rather than:

```text id="s1p8zi"
copy(B over C)
```

This allows upstream improvements to survive while retaining personal modifications.
